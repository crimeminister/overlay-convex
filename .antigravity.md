# Project Instructions (overlay-convex)

This repository is a Nixpkgs overlay focused on providing and customizing tools for the Convex Virtual Machine (CVM) ecosystem.
It centralizes package definitions for Convex-related CLI tools, libraries, and modules.

## Repository Structure

- `default.nix`: The main entry point of the overlay.
  It defines how packages are integrated into the Nixpkgs set.
- `pkgs/`: Contains subdirectories for individual package definitions.
    - `pkgs/<package>/default.nix`: The Nix expression for the package.
    - `pkgs/<package>/module.nix` (Optional): A NixOS or Home Manager module related to the package.
- `.antigravity.md`: (This file) Project-wide instructions, architectural patterns, and workflows.

## Key Conventions & Architectural Patterns

### 1. Package Definitions
- Use `self.callPackage` in the root `default.nix` for packages defined in `pkgs/`.
  This ensures they can benefit from dependency injection and overrides within the overlay.
- For overrides of existing Nixpkgs packages, use the `super` argument in `default.nix` to access the original package.
- Prefer `stdenv.mkDerivation` or specialized builders like `buildGrammar` or `emacsPackages.trivialBuild` as appropriate.
- When packaging Emacs major modes or modules (such as `convex-ts-mode`), use `emacsPackages.trivialBuild` to construct the derivation.

### 2. Versioning and Hashes
- Versions, hashes, and commit revisions (`rev`) **must** be passed as arguments to `callPackage` in the root `default.nix` for packages defined in `pkgs/`.
  This ensures reusability and centralizes version control.
- For packages with complex URL structures (e.g., including build IDs), the `version` argument passed should capture the full unique identifier necessary to construct the source URL within the package's `default.nix`.
- Use `lib.fakeHash` (or `""` in older Nix versions) when updating a package to trigger a build failure that reveals the correct SRI hash.

### 3. Modules
- If a package requires complex configuration, include a `module.nix` in its directory and expose it if necessary.

### 4. Code Formatting
- Always apply `nixfmt` to Nix files (`.nix`) in this repository after editing to ensure that formatting is maintained.
- Always format Clojure/Babashka files (`.clj`, `.cljs`, `.cljc`) after editing using `@chrisoakman/standard-clojure-style` (e.g. by running `npx @chrisoakman/standard-clojure-style fix <paths>`).

### 5. Package Update Checks
- Whenever a new package or module is added to the overlay, a corresponding Babashka task to check for updates **must** be created in `bb.edn`.
- For packages with Git tags or releases, use `check-github-package-update` from the `overlay.version` namespace.
- For packages pinned directly to a Git commit, use `check-github-commit-update` from the `overlay.version` namespace.
- Prefer using shared functionality (such as functions in `overlay.version` or `overlay.system`) as part of those tasks.
- If code written for an update check is potentially useful for future, similar tasks, it **must** be factored out into a utility namespace (e.g., under `bb/`) and required by the tasks.
- Any added utility functions **must** include comprehensive unit tests (under `test/`) and documentation (docstrings).

### 6. Documentation Formatting (One Sentence per Line)
- When writing or editing documentation (such as Markdown files like `README.md` or this `.antigravity.md`), prefer formatting prose using the **"one sentence per line"** convention (semantic line breaks).
- This ensures clean, granular Git diffs, as modifications to a sentence only affect that specific line rather than causing reflows across the entire paragraph.
- The formatting rules of Markdown or other technical documentation formats must still be respected to avoid poorly formatted output:
  - Do not introduce double newlines within a single paragraph unless you explicitly intend to start a new paragraph.
  - Ensure list items, tables, code blocks, and blockquotes maintain their appropriate structural syntax.

## Common Workflows

### Adding a New Package
1. Create a directory `pkgs/<new-package>`.
2. Add a `default.nix` in that directory.
3. Register the package in the root `default.nix` using `self.callPackage`.
4. Verify the build: `nix-build -E 'let pkgs = import <nixpkgs> { overlays = [ (import ./default.nix) ]; }; in pkgs.<new-package>'`.
5. Add a Babashka task in `bb.edn` to check for updates, reusing shared functionality and factoring out utilities as required.

### Updating a Package
1. Identify the source of truth for the version (either `default.nix` or the package file in `pkgs/`).
2. Update the `version` (and `rev` if applicable) and set the `hash` (or `sha256`) to `lib.fakeHash`.
3. Run `nix-build` and update the hash with the one provided in the error message.
4. If a `passthru.updateScript` exists, prefer using it via `nix-shell --run ./pkgs/<package>/update-script`.

## Testing & Validation

To test a package build in the context of this overlay:

```bash
nix-build -E 'let pkgs = import <nixpkgs> { overlays = [ (import ./default.nix) ]; }; in pkgs.<package-name>'
```

Alternatively, if you have a local `nixpkgs` checkout:
```bash
nix-build -I nixpkgs=/path/to/nixpkgs -A <package-name>
```

## Security & Ethics
- Never commit secrets or API keys to this repository.
- Ensure all source URLs use HTTPS.
- Audit package dependencies for security vulnerabilities where possible.
